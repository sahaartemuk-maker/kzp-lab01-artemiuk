# Звіт до лабораторної роботи № 3

## 1. Тема, номер і варіант
- Тема: Спадкування, інтерфейси й поліморфізм у Java-проєкті
- Предметна область: Спортивні тренування, варіант 2 (незмінний)
- ОС: macOS (Apple Silicon), Java 21; CI — Windows, macOS, Ubuntu

## 2. Мета роботи
Розділити сутність `Training` на підтипи з різною поведінкою, описати види
тренувань через `enum`, реалізувати узгоджені `equals`/`hashCode` і обробляти
всі записи через спільний тип, зберігши формат входу й показники попередніх робіт.

## 3. Стан до і після
| | ЛР № 2 | ЛР № 3 |
|---|---|---|
| Один запис | `final class Training` | об'єкт `IndoorTraining` або `OutdoorTraining` |
| Спільні поля | у `Training` | у абстрактному `Training` |
| Вид | текст | текст + `TrainingKind` |
| Відмінна поведінка | — | `load()` у підтипах |
| Створення | `new Training(...)` | фабрика `Training.of(...)` / `fromCsv` |
| Рівність | усі поля | `getClass()` + усі поля, `final` у базовому класі |

## 4. Базовий тип
`public abstract class Training`: поля `date`, `kind`, `type`, `minutes`,
`distanceKm`, `calories` (усі `private final`). Інваріанти перевіряє статичний
`validate(...)` у тому ж порядку, що в ЛР № 2; захищений конструктор делегує
приватному через `this(validate(...), ...)`, тому некоректний об'єкт не
створюється (і SpotBugs не фіксує `CT_CONSTRUCTOR_THROW` для нефінального класу).
Абстрактний метод — `double load()`. Обрано абстрактний клас, а не інтерфейс,
бо підтипи мають спільний стан і спільну реалізацію (геттери, `label`,
`equals`, `toString`).

## 5. Підтипи
- `IndoorTraining` (плавання, йога): власне правило — вид має бути «у приміщенні»;
  `load() = minutes × intensity`.
- `OutdoorTraining` (біг, велосипед, ходьба, інші): правило — вид не «у приміщенні»;
  `load() = minutes × intensity + distanceKm × 2`; додатковий метод `paceMinPerKm()`.

Обидва `final`, перевизначають `load()` з `@Override`.

## 6. enum
`TrainingKind`: `RUNNING("Біг", outdoor, 1.5)`, `CYCLING("Велосипед", 1.2)`,
`WALKING("Ходьба", 0.8)`, `SWIMMING("Плавання", indoor, 1.4)`,
`YOGA("Йога", indoor, 0.6)`, `OTHER("Інше", outdoor, 1.0)`.
`fromLabel` ігнорує регістр і пробіли; невідомий вид — `OTHER`, тому записи,
коректні в ЛР № 1–2, лишаються коректними.

## 7. equals і hashCode
Критерій: той самий клас і однакові дата, вид, хвилини, дистанція, калорії.
`hashCode = Objects.hash(getClass(), ...)` по тих самих полях. Методи `final`,
поля незмінні, тому об'єкт безпечний як ключ `HashMap`. Перевірено тестами
`HashSet` (два рівні записи → 1 елемент) і `HashMap` (пошук рівним ключем).

## 8. Поліморфізм
`TrainingStats.totalLoad()` проходить `List<Training>` і викликає `load()` —
без `instanceof`, `if` чи `switch` за підтипом. Новий підтип не вимагає змін
у звітності. Тип обирається один раз — у фабриці `Training.of`.

## 9. Тестування
Нові: `TrainingKindTest`, `PolymorphismTest` (вибір підтипу, різні формули,
нулі, поліморфна колекція, хибний вид для підтипу, хибний спільний стан,
`HashSet`/`HashMap`, нерівність різних підтипів), `RegressionTest`
(перевірка навантаження 370.70 / 178.00). Попередні тести збережено; у них
`new Training(...)` замінено на `Training.of(...)`, бо клас став абстрактним.

## 14. Відповіді на контрольні питання
1. Зберігає спільні поля й інваріанти в одному місці.
2. `extends` — успадкування класу (один), `implements` — реалізація інтерфейсів (кілька).
3. Щоб заборонити створення «загального» об'єкта й вимагати реалізацію абстрактних методів.
4. Ініціалізує й перевіряє спільну частину до полів підтипу.
5. Що метод справді перевизначає метод базового типу.
6. Виклик реалізації фактичного об'єкта через змінну базового типу; розгалуження не потрібне.
7. Інтерфейс — для спільної можливості без стану; абстрактний клас — для спільного стану й коду.
8. «Є різновидом» — спадкування; композиція — «містить» (поле іншого класу).
9. Щоб разом із константою зберігати пов'язані дані й поведінку.
10. Кожна константа — єдиний екземпляр.
11. Рівні об'єкти мають однаковий хеш; `equals` рефлексивний, симетричний, транзитивний, узгоджений.
12. Після зміни хеш інший — об'єкт «губиться» в кошику.
13. Через `getClass()` у `equals`: різні підтипи — різні сутності.
14. Викликає спільний метод, а реалізацію вибирає JVM.
15. `subtypesCalculateLoadDifferently`.
16. `equalObjectsHaveSameHashAndOneSetEntry`, `hashMapFindsLogicallyEqualKey`.
17. `sealed` обмежує підтипи переліком у `permits`.
18. Інакше логіка дублюється й новий підтип вимагає правок у багатьох місцях.
19. Усі тести ЛР № 1–2 і регресійний звіт.
20. `totalLoad()`: одна сума для будь-яких підтипів.

## 15. Висновки
Модель розділено на абстрактний базовий тип і два підтипи з різною формулою
навантаження; `enum` фіксує види; рівність узгоджена й перевірена в колекціях;
звіт сумісний із попередніми роботами. Це основа для наступної роботи.
